## Narrow ports

These are consumer-owned application contracts, not wrappers exposing whole SQLite stores or runtime classes. Prefer existing feature/shared DTOs and the existing attention resolver result union. Introduce only capabilities actually used by the extracted implementation.

- Attention resolution consumes a durable operation port: find the typed pending attention, read terminal operation/resolution state, claim/begin/retry/settle delivery, and read/write an operation replay. Its writer port exposes capability availability, current writer state, synchronous response delivery, and asynchronous guidance delivery. Guidance delivery accepts session ID, operation key and text; its concrete composition adapter owns runtime acquisition, turn queuing/start, session persistence and activity translation. A policy port exposes replacement authorization and explicit enable/disable; a settlement callback publishes the existing ordered projection/events.
- Checkpoint coordination consumes a retained-plan reader with `refresh(sessionId)` and typed current plan/identity/publication data, an activity reader for the existing active-writer policy, an acceptance port returning `OrgPlanCheckpointRecordStatus`, and a pending-handoff port for add/find/list/resolve. A writer port exposes resolve/reject and a guarded recover operation; an autopilot port exposes accepted/failure/recovery operations. Failure response construction accepts a reason code plus bounded expected/observed fields; composition supplies correlation IDs and diagnostics.
- Deadline owners consume `schedule(callback, delayMs): () => void`, `now(): string`, and the required writer/persistence callbacks. Keep opaque timer handles and platform clocks inside composition's concrete adapter. Each owner provides `responseSettled(sessionId, requestId, outcome)` and `disposeSession(sessionId)`/`dispose()` as needed. The checkpoint owner also exposes `failPending(sessionId, recoverBoundary)`.
- Settlement publication remains one composition adapter: derive remaining blocking interactions, update activity, append/publish `interaction.resolved`, append/publish `org-plan.attention-resolved` for attention, notify autopilot, then publish session status. Existing `OrgPlanAttentionReader` and `OrgPlanAttentionTransitions` stay the public read/stream ports.

## State, cancellation and shutdown

Each composed relay owns exactly one attention resolver, one attention acknowledgement owner and one checkpoint coordinator. The attention resolver alone owns its ephemeral in-flight promises. The acknowledgement owner alone owns its timer map; the checkpoint coordinator alone owns its timer map and recovery set. SQLite remains authoritative for claims, replay, pending interactions and checkpoints. Do not copy that durable state into a second mutable cache.

Composition constructs every concrete adapter and invokes lifecycle methods. It retains Fastify registration, authentication, public schemas/status codes, runtime origin normalization, provider routing, session creation/restoration, shared pending-interaction acceptance and generic interaction handling. Attention required/report retention remains in that shared acceptance/publication adapter; it is also used by the existing provider bridge and must not turn this extraction into a provider change. The application services import no platform, filesystem/process, Fastify or Svelte implementations. `AutopilotCoordinator`, its domain policies and `RelayApp` remain unchanged consumers/collaborators.

Shutdown currently sets `closing`, disposes provider recovery, closes host/retrieval work, drains capacity recovery, stops measurements, then for each session disposes autopilot/activity and cancels both Org deadline families. It preserves pending attention and checkpoint rows, dismisses other interactions, then stops runtimes, closes plan watchers and closes the database/auth handles. Service disposal must occupy those same deadline-cancellation positions before runtime/database teardown. Do not introduce new draining, settlement, or cancellation semantics for in-flight attention guidance or checkpoint recycle tasks: their current behavior is characterized only for the listed boundaries, not an authorization to redesign concurrent shutdown.

Manual Off and stale generation fencing belong to the existing autopilot/runtime owners. Resolution's explicit `resume` and `disableAutopilot` decisions retain their existing enable/disable authority; plan refreshes, timer callbacks and checkpoint writes never grant it. Pending human interactions still fence continuation. Timer tokens fence replaced deadlines; current runtime identity and active-turn checks fence asynchronous checkpoint recovery.

## Errors and response ordering

Attention HTTP mapping stays in `features/org-plan-attention/resolve/endpoint.ts`: malformed response 400, missing attention 404, stale/capability/writer/replacement conflicts 409, accepted/replayed 202. Guidance never enters replay/history payloads. Generic interaction responses cannot resolve attention.

Checkpoint typed failures preserve `planProjectionUnavailable`, `checkpointBoundaryAmbiguous`, `acceptedL1NotResolved`, `checkpointPayloadInvalid`, `planIdentityMismatch`, `rootNotOwner`, `rootTurnNotActive`, validator reason codes, `checkpointPersistenceFailed`, and `checkpointStateConflict`. Diagnostics use bounded correlation IDs; failure responses preserve the existing shared tool schema. A post-persistence exception becomes one explicit failed handoff. Failed writes, deadlines and late/duplicate settlements cannot schedule continuation. A successfully written response still waits for the owning root final; another turn's completion does not release it.

## Extracted application services

L6.2 implements the ownership above in `AttentionResolution`, `AttentionAcknowledgement`, and `CheckpointCoordination`. Their consumer-owned port types live beside the services. Composition creates one instance of each and supplies operation-specific adapters; it retains the shared attention read/transition/publication adapters, runtime construction, diagnostics, and lifecycle registration.

The checkpoint service exposes the plan read barrier separately from compact expansion and acceptance so composition preserves its existing order of plan refresh, session lookup, and request dispatch. A captured recovery capability exposes only its original active turn, a current-runtime predicate and recycle operation. The service checks the current root turn before recycling and runtime identity again after it, then saves the recovered session and releases the checkpoint through the existing recovery operation. Disposal cancels deadlines at the original shutdown position and preserves durable pending rows and existing in-flight recovery behavior.
