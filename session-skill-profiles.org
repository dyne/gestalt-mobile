* DONE [#A] Persist an immutable Effective Skill Selection per session
:PROPERTIES:
:ID: persist-session-skill-selection
:SKILLS: $context-mode:context-mode $vertical-slice-architecture $hexagonal-architecture $domain-driven-design $nodejs-backend-patterns $gestalt:development-testing $gestalt:verification-before-completion
:REVIEW_STATUS: UNREVIEWED

- Effort :: Large
- Goal :: Make every newly created Relay Session own a durable snapshot of the
  exact skills that were enabled when it was created, independently of later
  profile edits, deletion, project-default changes, or newly discovered skills.
- Notes :: Use the existing Sessions bounded context and SQLite session
  repository.  Keep global profiles behind the existing =SkillProfileStore=
  port and preserve the YAML/CLI contract.  The session aggregate owns an
  immutable Effective Skill Selection consisting of the optional selected
  global profile name plus a complete path-keyed snapshot.  The start-session
  REPR slice resolves a selected named profile over the existing default
  precedence, validates it before creating the aggregate, and persists the
  resolved snapshot before activation.  Runtime start, restore, supervisor
  recovery, and relay restart compile process-local Codex overrides from the
  session snapshot; they never reread the named profile.  A fresh catalog may
  be used only to disable skills discovered after the snapshot and ignore stale
  paths safely.  Existing database rows without a snapshot retain their legacy
  restore behavior and receive no invented historical selection.

** DONE [#A] Extend session creation, persistence, and activation as one use case
:PROPERTIES:
:ID: implement-immutable-session-skill-selection
:END:

- Why :: Saving only a mutable profile name would let later edits or deletion
  silently change a restored session, violating the session identity and the
  user's requirement that changing skills requires a new session.
- Change :: Extend the session start Request and client transport with an
  optional global skill-profile selection.  Add a domain value representing the
  selected profile name and complete enabled/disabled path snapshot to
  =RelaySessionSnapshot=, populate it only during creation, and preserve it
  unchanged through every aggregate transition.  Add a narrow profile-reading
  dependency to the start-session slice and resolve the effective profile,
  project default, CLI default, or native state against fresh discovery before
  the first save.  Refactor composition/runtime skill resolution to consume the
  stored snapshot for start and restore instead of the mutable profile record.
  Keep imported recent threads and pre-change rows backward compatible.
- Tests :: Add domain tests proving the snapshot is copied and never changed by
  lifecycle transitions; start-session endpoint/use-case tests for omitted,
  valid, unknown, and invalid named profiles; SQLite repository round-trip and
  old-row compatibility tests; composition/runtime tests proving later profile
  replacement/deletion and project/native changes do not affect restore, while
  newly discovered skills remain disabled; and relay-restart coverage for the
  same immutable snapshot.
- Done when :: A newly created session response and persisted row contain its
  complete Effective Skill Selection, every activation path launches with that
  selection, deleting or editing the source profile cannot affect the session,
  and legacy/imported sessions continue to operate under documented fallback
  behavior.
